Chat
Claude.ai · ChatGPT

Quick, one-off, no setup. Lives in your browser — paste in, get answer, done.

  • Idea → brief → Jira tickets → prototype → PR

Structured workflows

Same engine as Code, friendlier interface. Best for repeatable, scheduled routines.

  • "Summarize my unread emails every morning at 8am"
  • "Flag my Jira tickets with no updates this week every Friday"
  • Everything Cowork can do, Code can also do — different interface

How Claude Code Works

💡 Mental model: Treat it exactly like Claude Chat — you type, it responds. The only difference: Claude Code has access to your files. That one difference is what makes it powerful.
📁
Step 1 — Select a folder
Claude's world is bounded by what you point it to

Claude can read, edit, and create files — but only within that folder. Nothing outside is visible or touchable.

This matters: If your brief isn't in the folder, Claude can't see it. Put your work where Claude can reach it.

💬
Step 2 — Open a file and start chatting
Same as Claude.ai, just with file context
  • Open a file to give Claude context — "here's what I'm working on"
  • Type in the chat panel just like claude.ai
📺DEMO — open a file + start a chat
🧠
Step 3 — Your files become Claude's knowledge base
The more context in your folder, the better Claude performs
  • Your product brief → Claude understands the problem before you explain it
  • Your knowledge base docs → Claude knows your system, flows, terminology
  • Previous tickets or specs → Claude drafts consistent with what already exists

A well-organized folder is literally a better AI.

Module 1

What is a Markdown File?

A plain text file with a .md extension. No Word, no Google Docs, no hidden formatting — just text with simple symbols.

Why AI prefers markdown

  • Structure survives — Word docs get stripped silently when pasted into AI. Markdown keeps structure intact because the structure is the text.
  • Efficient — clean plain text = fewer tokens = faster, cheaper responses. No hidden XML or metadata bloat.
  • Direct reference — point to the file and the AI reads it in full, structure and all. No copy-pasting.
  • Universal — Claude, ChatGPT, Cursor — all handle it the same way.

Why your briefs & notes should live in .md

  • The AI can read them directly — no copy-paste, no lost context
  • They live alongside your code and tickets in GitHub — one place, always in sync
  • Version-controlled: "who changed the brief on Tuesday?" is a two-second answer
  • Work offline, never corrupt, never need a login
  • Upload to Confluence when ready — but the .md file stays as your source of truth
💡 This whole workshop started in a markdown file.

What Are Skills?

The Mental Model

Skills are pre-built AI workflows that run inside Claude Code. They can be triggered automatically based on the context of your conversation with AI, or by typing /skill-name in your terminal.

Think of them as smart macros — they know the right prompts, the right sequence of steps, and how to use your connected tools (Jira, Confluence, Databricks) together.

🔗 All Kueski PM skills live at github.com/kueski-dev/AI_agent_skills

How to use them

  • Trigger by name — type /skill-name in Claude Code to run it
  • Auto-triggered — some skills activate based on context (e.g. you share a Jira ticket)
  • Discover skills — type /help to list all available skills
  • Understand a skill — ask Claude "what does /problem-definition do?" before running it

Module 2

Human Judgment vs. AI

AI is cheap execution. Human judgment is the scarce resource.

AI is genuinely good at

  • Structuring and formatting output at scale
  • Synthesizing large amounts of text fast
  • Generating a first draft quickly
  • Running checklists without fatigue
  • Finding patterns in data
  • Simulating reviewers / stress-testing logic

Where AI falls short

  • Knowing the organizational context
  • Understanding unwritten constraints
  • Navigating stakeholder dynamics
  • Knowing what customers actually mean
  • Deciding what matters this quarter
  • Anything requiring real-world accountability
🧠 The shift: Because execution is now cheaper, human judgment is more important than ever. AI can generate the brief — but you decide if it's solving the right problem.
🎯 Your role: Stay in the driver's seat. Use AI to think faster, not to replace thinking.

Day 2 — Recap & Tips

Working on Your Initiative

A few things to help you go further before you dive in.

💡
Make /eng-review more accurate: harness engineering

Engineering review is only as good as the context it has. Repo-level documentation (an AGENTS.md or CLAUDE.md file in the repo) tells the AI what the service does, how it's structured, and what constraints matter — turning a generic review into a precise one.

What to ask your team:

  • Add an documentation files to the repo root describing the app's purpose, key flows, and architecture decisions
  • List the main entry points, notable dependencies, and any "don't touch without asking" areas
  • Include the test and deploy commands so the AI can reason about CI impact
  • Even a 20-line file makes a meaningful difference — it doesn't need to be exhaustive
🎨
For Prototype: leverage KDS + /user-story-generator

Run /user-story-generator on your brief to get screen-by-screen journey maps, then feed the detailed user stories directly into an AI prototyping tool alongside the Kueski Design System (KDS) repo.

  • Point the AI at the KDS repo so it uses real Kueski components, tokens, and patterns
  • The more granular your user story (from the skill), the more accurate the prototype
  • Iterate: tweak the story → regenerate → compare against KDS components

Module 3

CI/CD in Plain Language

🔁
CI — Continuous Integration
When you open or update a PR, robots run in the background: build the app, run tests, run style/security checks.

You don't run these by hand. GitHub Actions does it and posts green or red on the PR.

Think: "automatic proof the change still works."
🚀
CD — Continuous Delivery
After the change is trusted and merged, pipelines deploy built files to environments — staging first, production when ready.

Staging URL: kueskipay-aurora.kueski.codes

Think: "automatic copying of the built app to the right server."
📌 For PMs: You don't run CI/CD. You read its results (green/red on the PR) and validate on the staging URL after merge. That's your recurring seat.

🏛️ Governance Checks — Change management, Backstage, and CODEOWNERS-style validation run first. Ensures the right people and catalog metadata are in place. For a small copy change, these usually pass without you thinking about them.
🧪 Unit Tests — Automated tests run with coverage expectations. Red = "something that used to work might be broken." Same category as "the spreadsheet formula broke" — but for the app.
🔨 Build — The app is built the way we ship it (production-style, including bundle analysis). Confirms the code actually compiles into deployable assets.
🔍 Lint — Style and static checks: naming, patterns, TypeScript/ESLint rules. Often the fastest feedback on small mistakes.
🛡️ Quality / Security — SonarQube runs for quality signals; Snyk runs for dependency and security scanning. Second opinions before humans spend deep time.
👥 Code Review — Humans (and sometimes tools) read the change, comment, request edits, or approve. Treat approval as the gate — same instinct as not accepting every Google Doc suggestion without reading it.
✅ Merge — PR accepted; commits become part of master. The merge triggers merge_branch.yml — which runs tests again, builds, and deploys to staging automatically.
⚠️ A normal PM PR does not deploy to staging from the PR itself. The PR workflow is mostly "prove the change is safe." Staging deploy happens after merge.
Module 3

After Merge: Staging → Production

🔬
Staging (automatic)
Merge to master → triggers merge_branch.yml → lint + tests + build + Snyk + deploy to staging.

Staging URL: kueskipay-aurora.kueski.codes

QA and stakeholders can try the change before it reaches customers.
🌐
Production (deliberate)
release.yml is triggered manually. Someone chooses a commit, creates a GitHub Release, and deploys to prod.

Prod URL: prod.kueskipay.com

Merging to master ≠ customers see it tomorrow.

The Google Drive Analogy — Final Act

Users don't clone GitHub. They open a URL. That URL fetches the current published bundle.

The "save" was merge + deploy, not Cmd-S in a doc — but the mental model is the same: everyone always sees the latest published version.

⚠️ Flows differ by repo. Branch names, what triggers staging, how production is promoted — all live in that repo's CI config. When in doubt, read .github/workflows/ or ask AI.

Module 3

What Makes a Good Copy Ticket

On Web

✓
Exact copy — before and after
Quote verbatim. Not "make it friendlier" — quote both strings.
✓
Route or URL
e.g. /pay/aplicar — same precision as "open this link on staging."
✓
Staging link after merge
So anyone can verify in under a minute.

On Mobile

✓
Tap-by-tap navigation path
From app open. No URL bar on mobile.
✓
Platform: iOS / Android / both
✓
Deep link if available
+ screen name from design if it helps.
🤖 Why this helps AI: Exact copy lets search and i18n lookup land on one or a few files instead of guessing. Vague tickets force the model to invent scope; specific what + where keep the PR small and reviewable.
Module 3

Understanding Any Repo's CI/CD

Staging and production paths are not identical across repos. When you need the truth for a codebase, use this prompt:

# Paste this into your AI with the repo context attached:

Explain in plain language (no jargon) how this repo gets to staging and production.
Use exactly two bullets:

Staging — one or two short sentences on what happens and who/what triggers it.
Production — same for production.

Keep the whole answer brief enough to skim in under a minute.
📁 Ask it to cite the workflow file names if you want to double-check against GitHub's Actions tab. Look in .github/workflows/ of any repo.
✅ For kueskipay-frontend: PR opens → CI checks → review → merge → auto-deploy to staging → manual release to prod.
